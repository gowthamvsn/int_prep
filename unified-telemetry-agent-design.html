Unifying app, infra & analytics logs for an LLM agent — the real engineering design

Not a hypothetical. Every design decision below is sourced to Honeycomb's Query Assistant (wide-event logs/traces/metrics from customer apps and infra, an LLM query layer on top) and Datadog's Bits AI (a multi-source SRE agent) — two companies that published unusually specific detail on exactly this problem.

the setup

What's actually being ingested

Honeycomb's product unifies traces, logs, and metrics from a customer's application and infrastructure into one wide-event model — some customer schemas carry over 5,000 unique fields. Datadog's Bits AI reasons across an even wider set: metrics, logs, traces, infra metadata, RUM, network path, and profiler data, to find the root cause of a production incident. Both are real companies solving your exact three-source problem, at production scale, in public.

issue 1 · vocabulary

Solved at ingestion, not at query time Honeycomb + OpenTelemetry

Customer app logs call it user_id. Infra metrics call it host_id. Analytics calls it actor_id. Honeycomb's real fix wasn't a synonym table — it was feeding the customer's actual, current schema straight into the prompt as grounding. The more durable, industry-standard fix is normalizing before anything reaches an LLM:

Design rule Put the normalization layer at the ingestion/collector tier, not in the prompt. Fixing vocabulary at query time means re-solving it on every request; fixing it at ingestion means you solve it once, per source, forever.

The gap OTel doesn't close: the AI engineer isn't the domain expert

Normalizing field names doesn't tell you which field actually means what a business person means by "the right data" — an AI engineer building this system usually isn't the person who knows that, say, order.status = 'held' is the field that actually predicts a failed checkout, three joins away from anything obviously named "checkout." Guessing at that mapping is how you ship a confidently wrong retrieval layer.

The real, established pattern for this — not invented for LLMs, but exactly what an LLM context-assembly layer needs — is a data catalog with a business glossary: tools like Lyft's Amundsen or LinkedIn's DataHub exist specifically so a domain expert (not the engineer) can annotate a table or field with its business meaning, link it to the metric/dashboard it feeds, and make that annotation discoverable by anyone building on top of it.

Design rule Build (or point at) exactly this kind of tool as the interface between the AI engineer and the domain expert: a lightweight registry where the expert answers "what's the right field for X, and how do I fetch it" once, in a UI, and that answer becomes a structured mapping the context-assembly layer reads from — instead of a Slack thread the engineer has to re-ask every time the schema changes.
issue 2 · context & tokens

Real numbers on what happens when you just "use a bigger context window" Honeycomb

The naive move — dump the whole 5,000-field schema into the prompt — blows GPT-3.5-turbo's context window outright. Honeycomb's shipped fix: only include fields that received data in the last 7 days. Recency as a cheap relevance proxy, not an embedding lookup. When that still wasn't enough, they truncated further — and are explicit that this was "hit-or-miss depending on if the most relevant fields... were truncated or not."

Counterintuitive real finding A bigger context window is not a free lever. Past a point, stuffing more tokens in made Honeycomb's system both slower and less accurate — the dial goes the wrong direction on both axes at once if you use "more context" as a substitute for actually filtering what's relevant.
issue 3 · memory

Memory is a carried object, not a transcript Honeycomb + Datadog

Honeycomb's real multi-turn mechanism: the existing query object from the last turn is included as a literal prompt component on the next one. Not chat history — one structured object, carried forward.

For a longer investigation across three sources, Datadog's Bits AI keeps an evolving hypothesis + evidence state: which theory is being tested, what's been checked already, so it never re-queries the same telemetry twice in one session.

Design rule Memory = a structured state object your orchestrator code owns and updates explicitly (a query object, a hypothesis record) — not something you ask the LLM to "remember" by making the context window bigger.
issue 4 · tool decision

Tool choice is a function of the hypothesis, not the question Datadog Bits AI

Datadog's Bits AI reasons across metrics, logs, traces, infra metadata, RUM, network path, and profiler data. The real, documented shape of its tool selection is not a classifier mapping "question type → one data source." It's a loop:

Design rule A static router ("classify the question, pick one source") cannot do this, because it decides before it has any evidence. Make the current hypothesis — not the raw user question — the input to tool selection, and let the loop re-route after every query result.
issue 5 · chaining makes it worse

The compounding-error math Honeycomb

Honeycomb tried the obvious "agentic" move — chain 3–5 LLM calls (draft → refine → validate) — and measured no tangible improvement. The real reason is arithmetic, not opinion:

0.9 × 0.9 × 0.9 × 0.9 × 0.9 = 0.59

a 90%-accurate step, chained 5 times, is 59% accurate end to end

Design rule Every extra LLM hop in a chain multiplies your error rate — it does not average it out. Don't chain "summarize infra → summarize app → summarize analytics → synthesize" as four separate calls unless you've actually measured each step near 100%, because a 4-hop chain at 95% per step is still only 81% end to end.
issue 6 · security, honestly

What they actually ship, and what they admit they haven't solved Honeycomb

"It's kinda like SQL injection, except worse and with no solution today." — Honeycomb engineering, on prompt injection against their query assistant

Real, ongoing: "people are already attempting prompt injection in our system today... several people attempt to extract information from other customers." Their shipped mitigations, none of which claim to fully solve it:

MitigationWhat it actually bounds
LLM output is a query object, never raw executionA deterministic parser/validator sits between the model and the database
Action is non-destructive and undoableWorst case is a bad query result, not a bad write
