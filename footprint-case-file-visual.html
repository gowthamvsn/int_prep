The refund that shouldn't have happened —
and the six-line trail that explains it

A walkthrough of footprintjs / agentfootprint, the open-source framework by Sanjay Krishna Anbalagan that makes an AI agent's decisions traceable, provable, and auditable — step by step, in its own words, with the real example from the project's own docs.

Source: github.com/footprintjs/footPrint  ·  github.com/footprintjs/agentfootprint  ·  MIT licensed
the opening problem

An agent that's "up," fast, and confidently wrong

A loan pipeline rejects an applicant — call him Bob. The code didn't crash. The server didn't time out. The answer even reads as reasonable. Bob asks the obvious question:

Bob"Why was I rejected?"

A normal log tells you what happened: status: REJECTED. It does not tell you why the system believed that was correct — which fact, which rule, which comparison actually produced that word. That gap is the whole problem this project exists to close.

step by step

How the trace is actually built footprintjs

Business logic isn't written as one big function — it's written as a graph of small, named stages, each one working on a shared, watched piece of state called the scope. Every stage that reads from the scope, writes to it, or makes a decision based on it gets that action recorded automatically, as it happens — nobody writes a log line by hand.

Read left to right, that's the pipeline running forward. Read right to left, it's the answer to Bob's question — an actual chain of cause and effect, not a guess reconstructed from scraps of log text:

Stage 1: Write creditScore = 580, dti = 0.6, employmentStatus = "self-employed" Stage 2: Read creditScore = 580 → Write riskTier = "high" Stage 3: Read riskTier = "high" → [Condition] "high" eq "high" ✓ → RejectApplication Stage 4: Write decision = "REJECTED — DTI 60% exceeds 43%; credit score 580; self-employed < 2yr"
What the AI can now honestly say to Bob "Your application was rejected because your debt-to-income ratio of 60% exceeds the 43% maximum, your credit score of 580 falls in the 'fair' tier, and your self-employment tenure of 1 year is below the 2-year minimum." — generated from the trace, not invented by the model reading between the lines of a log file.

The project's own vocabulary table, precisely — every term maps to something you already understand from other systems:

footprintjs term= the thing you already know
scopethe run's shared state (working memory) — but every read/write is tracked
decider / select()a router (one branch) / parallel fan-out (many branches)
recorderan observer, called on each read/write/decision
narrativethe execution trace, rendered as plain English — the LLM-readable form
commit logthe ordered record of what each stage wrote — powers time-travel replay
memory — real API

One recording, three consumers, zero extra instrumentation agentfootprint

Memory isn't a single mechanism here — it's a factory, and the numbers are exact: 4 types (episodic / semantic / narrative / causal) × 7 strategies (window / budget / summarize / topK / extract / decay / hybrid). The interesting one is causal: instead of storing raw conversation history, it stores the same decision-evidence snapshots as the trace above — which means one recorded run can be replayed later, handed to a cheaper model for fast triage on a similar future decision, or exported as training data. human-in-the-loop — real API

Pause for a person, resume on a different server, days later

Because state commits per-stage (the same transactional model behind the loan trace), a run can stop mid-flow, wait for a human, and pick back up anywhere — this is the literal documented call shape:

const out = await agent.run({ message: 'Process refund' }); if (isPaused(out)) { const checkpoint = out.checkpoint; // plain JSON, persist it anywhere // ...hours or days later, possibly on a different server: await agent.resume(checkpoint, userDecision); }

The same checkpoint mechanism backs a tool calling pauseHere(...) or askHuman(...) mid-stage — and because the commit log is what makes this possible, it's the same feature that lets you rewind a run to any prior stage's exact state for debugging, not a separate system bolted on for human approval specifically.

engineering, not just concepts

The parts that show this was built for production

  • Tree-shaking is CI-proven, not promised — a real test in the repo (test/esm-packaging.test.ts) bundles a minimal import { flowChart } and asserts the recorder, detach, and trace layers get pruned out. Dual true-ESM/CJS build, subpath exports (footprintjs/trace, footprintjs/detach, footprintjs/advanced) so each layer is independently tree-shakeable.
  • Deferred observers with honest backpressure — a heavy recorder can run "one beat behind" on a bounded queue ({ delivery: 'deferred' }) instead of blocking the engine's hot path, with a named backpressure policy when the queue fills: drop-oldest / sample / block.
  • Fire-and-forget child flowcharts via scope.$detachAndForget(driver, child, input) — six real built-in drivers: microtask / immediate / setImmediate / setTimeout / sendBeacon / workerThread, plus a custom-driver protocol.
  • 60+ typed observability events across 18 domains — agent · composition · context · stream · tools · skill · memory · cache · cost · permission · eval · embedding · pause · error · fallback · resilience · reliability · risk. (Worth flagging: an earlier draft of this page cited "47 events across 13 domains" from a secondhand source — that number was wrong. This is the real, current count, checked directly against the project's own README.)
where the data comes from

Every fact the model sees has an address agentfootprint

A chat agent is fed more than one prompt: background facts about the customer, always-on rules, and skills that only switch on when needed. Instead of mashing all of that into one string, each piece declares two things up front — where it's allowed to land, and when it's allowed to fire. That's the whole abstraction:

The payoff of labeling things this precisely: nothing enters the model's context by accident. If Bob's decision was influenced by something, that something has a name, a slot, and a reason it was let in — which is exactly what you need to walk the trace backward when the decision looks wrong.

how it decides — real CLI output

Picking the right tool — and catching it when it doesn't agentfootprint

Two tools with near-identical names or descriptions get picked interchangeably by the model. This is the literal, unedited output of running the project's own confusability linter against a real tools file:

$ npx agentfootprint-lint-tools tools.json --threshold 0.94 --strict ✗ CONFUSABLE 0.9445 get_fcns_database <> influx_get_fcns_database hint: names differ only by 'influx' — make the descriptions say WHEN to choose each ~ warn [enum-in-prose] influx_get_port_ranking.metric suggest: "enum": ["avg_iops","peak_iops","mbps"]

That's a real pairwise-embedding similarity score (0.9445) against a real --threshold 0.94 flag — two tools named a single word apart, caught before a single live user ever triggered the mix-up. The linter is pluggable on the embedder and cached by content hash, so re-running it costs nothing until a tool description actually changes.

The same geometry runs live, via an observer attached at build time:

const choices = toolChoiceRecorder({ embedder: staticEmbedder() }); const agent = Agent.create({ provider, model }) .watch(choices) .build(); await agent.run({ message: 'refund order 4471' }); console.log(await choices.getFlagged()); // calls where the tool choice was a near-tie

Design split, stated directly by the project: "agentfootprint owns the detection — the scores, the ties, the recorded margins; you own the policy — the threshold, the embedder, the rewrite." It flags; it doesn't decide for you what to do about a flag.

The other lever: don't show every button at once Tools aren't a fixed catalog sitting in front of the model on every turn. A tool only enters the list once its skill has been explicitly unlocked — turn 1 might expose one general tool, turn 4 (once the model has scoped into "this is a refund") exposes five refund-specific ones. Fewer buttons on the desk at any moment is itself a reliability feature, not just a cost saving.

Tamper-evidence, in the project's own real output

A causal trace only means something if nobody edited it after the fact. auditExport() hash-chains every typed event — decisions, tool calls, permission verdicts, costs — into an append-only bundle; verifyAuditBundle() re-checks it entirely offline, no agent or LLM involved. This is the literal documented behavior when one record in the chain is altered:

verifyAuditBundle(bundle) → { valid: false, brokenAt: #16, reason: 'hash mismatch' }

Not "something looks wrong somewhere" — record #16, specifically. And a genuinely useful efficiency number from the same docs: their trace-debugging toolpack lets a cheap model walk a captured run by ID rather than reading the whole thing, and found a planted bug after reading 9.5% of the trace.

keeping the two apart

What this fixes, and what it deliberately doesn't

Not this system's job

Deciding what the refund policy should be. If the 30-day rule itself is wrong or outdated, that's a product and policy call — no amount of tracing fixes a bad rule.

Exactly this system's job

Making sure that whatever the rule is, when the agent breaks it, someone can find the exact cause in minutes — proven, not guessed — instead of never finding out at all.

One more boundary worth naming: this whole toolkit tells you why an answer happened. It never tells you whether the answer was right — that's still a separate job for a standing evaluation set, checked continuously. A system can have a perfect trace on a badly wrong answer; tracing and evaluation are both required, and neither substitutes for the other.
